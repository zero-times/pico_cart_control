# Pico 诊断日志：采集、时间同步与验收

本指南对应固件 `0.2.2`。手机继续通过 BLE 控制小车；USB 用于 Pico 调试和日志读取。
诊断的目标是关联手机命令、蓝牙链路、传感器与停车事件，同时让导出与清理的结果可核验。

## 接口与存储范围

| 通道 | 实际接口 | 用途 |
|---|---|---|
| 手机 BLE | WS-B01/Pico-BLE → UART0，GP0/GP1，115200 bps | 控制、校时、查询、主动导出和确认清理 |
| Pico USB | MicroPython USB CDC | 运行中读取诊断、REPL 与固件上传 |
| 可选 BLE 改线 | UART1，GP4/GP5 | 只有实际切换底板焊盘且同步修改固件配置时使用 |

USB CDC 不等于 UART1。默认接线仍使用 UART0 连接蓝牙模块，GP15 仅供蓝牙 STATE。
USB 诊断不读取移动命令，也不接受校时、清理等写操作。

Pico 使用 `192` 条 RAM 环形缓存，缓存满后覆盖最旧记录，断电或固件重启后不保留。
日志不在行驶过程中写 Pico Flash。正常运行还会追加周期快照，因此“不手动 clear”不代表
断连前的记录永远保留；发生异常后应及时通过 USB 采集，或恢复 BLE 后主动导出。

`overwritten` 表示缓存因容量不足发生的覆盖，不等于传输丢包。`used_pct` 是当前容量占比。
达到 `90%` 时手机提示同步日志，用户决定何时导出；连接本身不会实时搬运整份缓存。

## 时间与固件版本

BLE 通道就绪后，手机的首条应用指令为：

```text
time sync <UnixMillis>
```

`UnixMillis` 是手机当前 Unix 毫秒时间。手机随后查询日志容量和运行状态；界面显示同步状态，
也允许用户主动重新同步时间。设备时间查询和同步回包使用相同格式：

```text
time synced=1 unix_ms=<UnixMillis> uptime_ms=<UptimeMillis> fw=0.2.2
```

日志中的字段含义如下：

| 字段 | 含义 |
|---|---|
| `s` | 当前启动期间的全局记录序号，用于关联事件和清理边界 |
| `t` | 单调启动时长，单位毫秒；控制超时不依赖手机墙上时钟 |
| `u` | 校时后的 Unix 毫秒时间；尚未校时为 `0` |
| `fw` | 产生日志的 Pico 固件版本，此版本为 `0.2.1` |
| `e` | 事件类型，例如 `boot`、`time_sync`、`ble_disconnect`、`stop` |

`info` 回包也包含 `fw`，但协议版本与固件版本是不同字段。导出时保留原记录的版本和时间，
不要用导出时刻替换事件发生时刻。

校时仅建立单调时长到 Unix 时间的映射，不调整控制时钟。校时前的记录仍保留 `u=0`；
可以用同一次启动中的 `time_sync` 事件作为锚点，按 `t` 差值人工估算早期事件的墙上时间。
这不是对早期记录的精确补时，精度受手机时钟、BLE 传输延迟和同步时机影响。
重启后应重新校时，不能把另一轮启动的锚点套用到旧日志。

## 主动导出和确认清理

在 Android 调试页连接设备，确认 Pico 心跳可用，再按以下顺序操作：

1. 检查固件版本、时间同步状态和缓存容量；未同步时先主动同步时间。
2. 点击硬件日志同步/导出入口。界面显示接收进度，完整记录保存到现有
   `pico_cart_debug.log` 的 `[hardware]` 分类，不把每条记录刷到普通命令列表。
3. 等待接收、完整性校验和本地保存均成功。导出中断、超时、缺号或保存失败时，按不完整处理，
   不清理 Pico 缓存；排除原因后重新导出。
4. 成功后用户确认是否清理本次已导出的记录。选择保留不会删缓存；选择清理仅删除本次快照
   最后序号及之前的记录，保留导出期间新生成的事件。
5. 如需主动清空所有缓存，使用清空入口并确认。这与“清理已导出记录”不同，会删除尚未导出的
   旧记录；清理本身和后续运行仍可产生新日志，因此界面不必永久显示 `0` 条。

导出是一次快照，导出期间 Pico 继续记录新事件。不要把“接收到了最后一条记录”视为完整：
手机必须检查导出 ID、唯一序号、总条数和结束标记，防止中间漏包或混入上一轮导出记录。
硬件日志与普通手机日志共用持久日志文件，文件约 `2MB` 时轮转，另保留 `.1`、`.2`、`.3`。
调查较早的事件时应一并保存轮转文件。

## 线协议参考

下列尖括号字段均为占位说明，不是实车采集样例。发命令时用实际数字替换，并以换行结束。

| 指令 | BLE | USB CDC |
|---|---|---|
| `time status` | 查询同步状态 | 查询同步状态 |
| `time sync <UnixMillis>` | 同步时间 | 不支持 |
| `info`、`status` | 查询 | 查询 |
| `hwlog status` | 查询容量 | 查询容量 |
| `hwlog dump` | 开始快照导出 | 开始快照导出 |
| `hwlog clear <LastSequence>` | 清理已导出范围 | 不支持 |
| `hwlog clear` | 主动清空 | 不支持 |
| 行驶、模式、参数设置指令 | 按既有 BLE 控制规则处理 | 不支持 |

容量回包：

```text
ok hwlog_status n=<Count> cap=192 used_pct=<IntegerPercent> overwritten=<Count> exporting=<0or1> fw=0.2.2 synced=<0or1>
```

一次导出的开始、记录与结束：

```text
ok hwlog_export n=<Total> x=<ExportId> last=<LastSequence> fw=0.2.2
hwlog x=<ExportId> i=<Index> n=<Total> s=<Sequence> t=<UptimeMillis> u=<UnixMillisOrZero> fw=0.2.2 e=<Event> ...
hwlog_end n=<Total> x=<ExportId> last=<LastSequence> fw=0.2.2
```

`i` 是本次导出的 1 基索引，必须完整覆盖 `1..n`，重复索引不得增加接收总数。
`x` 用于区分不同导出；`s` 是日志全局序号，`last` 是快照的清理边界。
开始与结束的导出 ID、总数、最后序号应一致；不能因为最后收到 `i=n` 就忽略缺号。

用户确认清理已成功保存的快照后，发送该快照的实际 `last`：

```text
hwlog clear <LastSequence>
ok hwlog_clear n=<RemainingCount>
```

导出过程中清理返回 `err hwlog_busy`。普通 `hwlog clear` 是主动全清，必须由用户确认后使用；
USB 不接受这两类清理操作。

## 从 USB 获取日志

采集时保持 `main.py` 运行，不发送 Ctrl-C，不让串口工具自动进入 raw REPL。
USB 会限流输出 `usb_log ...`，可同时发送只读诊断指令。需要使用 REPL 或重新上传固件时，
先关闭采集终端，让 `mpremote` 等工具独占串口。Ctrl-C 会退出主循环并经过固件停车清理路径，
不作为普通日志读取步骤。

安装串口终端并列出设备：

```bash
python3 -m pip install pyserial
python3 -m serial.tools.list_ports
```

macOS 的 Pico 端口通常形如 `/dev/cu.usbmodem...`，Linux 常为 `/dev/ttyACM0`，Windows 为 `COMx`。
以实际列表为准；Windows 可将以下 `python3` 换成 `py`。

打开终端，替换实际端口：

```bash
python3 -m serial.tools.miniterm /dev/cu.usbmodemXXXX 115200 --eol LF --raw
```

按顺序输入下列内容，每行回车，等待上一条响应再发下一条：

```text
info
time status
hwlog status
status
hwlog dump
```

观察 `hwlog_export` 开始和 `hwlog_end` 结束，保留二者及中间全部记录。
未连接手机时 `synced=0`、事件 `u=0` 是正常情况，USB 不负责设置时间。
使用 miniterm 的退出快捷键 `Ctrl+]` 关闭采集终端；不要用 Ctrl-C 打断 Pico 程序。
若终端支持保存会话，可将完整会话保存为 UTF-8 文本，文件名包含采集日期和固件版本；
同时记录端口、是否连接 BLE、异常操作和采集时间。不能只截取最后一条完成回包。

## 从 Android 获取日志

先按前述流程完整导出硬件日志，完成后用已授权的 ADB 连接手机。确认设备后拉取整个日志目录，
同时保留当前文件和历史轮转文件：

```bash
adb devices
adb pull /sdcard/Android/data/com.zerotimes.picocart/files/logs ./pico-cart-logs
```

只取本次当前文件时可用：

```bash
adb pull /sdcard/Android/data/com.zerotimes.picocart/files/logs/pico_cart_debug.log ./pico_cart_debug.log
```

在文件中定位 `[hardware]`、`fw=0.2.2` 和相应导出 ID；用 `s`、`t`、`u` 关联手机发送记录与
Pico 事件。手机日志行前的日期是手机落盘时间，Pico `u` 才是校时后的事件时间，二者不应混用。
如文件中只有请求记录而没有硬件日志，先检查导出是否完成、Pico 固件是否匹配、BLE 心跳是否正常。

## 可执行硬件验收清单

下列项目需要连接实物后执行并保存原始日志。停车相关操作在轮子架空且可以立即急停的条件下进行。

| 场景 | 操作 | 通过条件 |
|---|---|---|
| USB 独立读取 | 手机断开 BLE，保持 `main.py` 运行，通过 USB 执行全部只读命令 | 返回查询与完整导出；有带版本的限流事件；无需 Ctrl-C；控制主循环保持运行 |
| USB 权限边界 | USB 发送 `f 0.1`、`time sync ...`、`hwlog clear` | 明确拒绝，不行驶、不改时间、不清缓存 |
| 首次自动校时 | Pico 重新上电，先取 USB 未校时记录，再连接 Android | BLE 首条应用指令为 `time sync`；界面显示成功；新记录有 Unix 时间，旧记录仍 `u=0` |
| 主动重校时 | 通过界面主动同步，再查 `time status` | 新同步结果可见；`t` 连续递增，控制超时不因校时跳变 |
| 90% 容量提示 | 让缓存持续积累至至少 90%，连接手机或主动刷新容量 | 显示近满提示和同步入口；不会自动持续导入；不未经确认清理 |
| 环形覆盖 | 持续运行到容量满，再产生事件并查询 | `n` 不超过 `192`，覆盖计数反映覆盖；最新记录可导出；旧记录覆盖被明确说明 |
| 正常完整导出 | 主动导出并拉取 Android 文件 | 同一 `x` 的索引无缺号，总数与开始/结束一致，所有记录带 `fw`；保存成功才出现清理确认 |
| 缺号或重复记录 | 在可控的测试传输中丢弃一条中间记录，或重复一条后补结束 | 不以最后索引冒充条数；缺号报告不完整；重复记录不增加有效计数；不得触发成功清理 |
| 中断和超时 | 导出中断开 BLE，恢复后重新导出 | 显示不完整/超时；不清缓存；新导出 ID 与旧导出分开，旧结束消息不误判新导出完成 |
| 本地保存失败 | 使用可控故障令日志写入失败 | 不显示保存成功，不弹出成功清理确认；错误可见；Pico 缓存保留 |
| 取消清理 | 完整保存后选择保留 | 已导出记录仍可查询/再次导出，之后仍按环形规则覆盖 |
| 清理保留新日志 | 开始导出，期间制造可识别的新事件，成功后确认清理 | `s <= last` 的快照范围被清理；`s > last` 的新事件仍可导出 |
| 主动全清与忙状态 | 取消一次主动清空，再确认全清；另在导出中尝试清理 | 取消不删除；确认才全清；导出中返回 `err hwlog_busy`；允许出现清理事件和新快照 |
| 异常事件关联 | 分别制造 BLE 断开、HX711 异常、急停与前障碍后及时取日志 | 能找到对应事件/停车原因及版本；USB 和 BLE 导出的同一记录 `s/t/u` 一致 |
| 导出期间停车 | 导出同时做低速点动、松手、stop、急停或断连 | 导出不阻塞控制处理，停车遵守既有安全行为；失败路径仍留下诊断依据 |
| 断电边界 | 保存一份记录，重启 Pico 再查容量和时间 | 不宣称恢复旧 RAM 日志；同步状态重置并在手机连接后重建 |
| REPL 与刷写 | 关闭采集工具，进入 REPL/上传后恢复运行 | 串口可重新占用；Ctrl-C 停车；既有固件上传流程可用 |

缺号、重复、保存失败等不易在实物稳定复现的场景，可先用模拟数据或故障注入验证界面和协议处理，
但必须标记为模拟验证；实际 USB 数据读取、串口中断行为、BLE 时序与电机停车仍需实物验收。
